## 六、根因分析

### 6.1 根因一：异构流顺序被直接 concat

第一段的 Stream 0 是视频，后两段的 Stream 0 是音频。如果 concat 实现按流序号直接处理，而不是按 `codec_type` 显式映射，就会把不同类型的轨道错误连接。

这可以解释：

- 拼接输入明明有三段，成片却只看到其中一段。
- 有效视频轨约七秒后结束。
- 后续片段没有进入正确的视频轨。

### 6.2 根因二：没有统一编码参数

第一段是 H.264 High Profile，后两段是 Main Profile，封装器和音频配置也存在差异。直接流复制会保留不同素材原始的 codec 参数和时间戳，不满足安全拼接条件。

### 6.3 根因三：输出时间戳或容器 Duration 异常

三个源视频实际总时长约为：

```text
7.041667 + 8.041667 + 7.041667 = 22.125001秒
```

最终成片显示 `1分19秒`，说明最终容器的 Duration、轨道 PTS/DTS 或编辑器读取到的时间线结束点已经异常。

当有效视频轨只剩约七秒，而容器仍声明有 79 秒时，播放器通常会在视频轨结束后继续显示最后一帧，因此产生“十秒后一直静止”的现象。

### 6.4 根因四：拼接后没有检查最终 Asset

Agent 在 concat 前探测了三个输入素材，但 concat 完成后没有对 `a_cmZChFc` 执行：

- `media_probe`
- 最终 Duration 校验
- 视频轨帧数校验
- 分段边界抽帧
- 重复帧检测

因此，接口返回 `success: true` 就被当成制作成功。实际上它只表示命令完成，不表示输出文件内容正确。

## 七、解决方案

### 7.1 拼接前强制标准化

所有输入视频先统一为相同规格：

```text
视频：H.264 High 或 Main，统一 Profile
分辨率：1280×720
帧率：24fps CFR
像素格式：yuv420p
视频时基：统一
音频：AAC-LC、44.1kHz、双声道
流顺序：Stream 0 = 视频，Stream 1 = 音频
起始时间戳：0
```

推荐先分别标准化，再 concat：

```bash
ffmpeg -i input.mp4 \
  -map 0:v:0 -map 0:a:0 \
  -c:v libx264 -profile:v high -pix_fmt yuv420p -r 24 \
  -c:a aac -ar 44100 -ac 2 \
  -fflags +genpts -avoid_negative_ts make_zero \
  normalized.mp4
```

### 7.2 concat 必须按媒体类型映射

禁止按 Stream Index 假定所有输入结构一致。必须显式使用：

```text
每个输入的第一个 video stream
每个输入的第一个 audio stream
```

如果输入 codec 参数不完全一致，禁止走 stream copy，必须重新编码。

### 7.3 重建时间戳

拼接时应为每段重置 PTS：

```text
视频：setpts=PTS-STARTPTS
音频：asetpts=PTS-STARTPTS
```

然后使用 concat filter 分别生成一条连续视频轨和一条连续音频轨。

### 7.4 增加最终成片硬校验

最终 Asset 必须满足：

```text
abs(最终视频轨时长 - 输入视频时长总和) <= 0.2秒
abs(最终容器时长 - 最终视频轨时长) <= 0.2秒
最终帧数约等于 22.125 × 24
```

本项目预期：

```text
最终时长约 22.13秒
最终帧数约 531帧
```

如果输出为 79 秒、只有约 169 帧，或者视频轨与容器时长严重不一致，必须判定拼接失败。

### 7.5 增加视觉 QA

至少抽取：

```text
0秒
7秒附近
15秒附近
结束前1秒
```

确认三个段落都实际出现，并检测尾部是否存在长时间重复帧。

## 八、最终诊断

该项目三段视频均已生成，最终拼接调用也传入了三个 Asset。问题发生在 Assembly：第一段与后两段的音视频流顺序、编码 Profile 和封装参数不同，但系统没有进行标准化，直接通过快速 `cut concat` 合并。

最终输出因此出现轨道映射或时间戳异常：只有其中一段约七秒的画面进入有效视频轨，后两段没有正确形成连续视频；同时容器或时间线 Duration 被异常写成约 1分19秒。有效视频结束后，播放器持续显示最后一帧，形成长时间静止画面。

核心修复是：拼接前统一流顺序和编码参数，按媒体类型显式映射轨道，重建 PTS/DTS，并在交付前对最终 Asset 执行时长、帧数和逐段视觉校验。
