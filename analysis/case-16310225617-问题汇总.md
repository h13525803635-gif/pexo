# Case 16310225617 问题汇总

## 一、结论摘要

项目 `16310225617` 的首要问题是：**原定三段视频，正式生成批次实际只生成了两段。**

1. 制作方案规划了 `seg1 / seg2 / seg3` 三段，但首轮只调用了 `seg1_march` 和 `seg3_awe`，没有生成 `seg2_reveal`。这与后台只看到两段视频一致。
2. 后面出现的 `seg2_reveal_k / k2` 属于异常后的补生成，不应被表述为原三段正常完成。它与第 3 段的多次重试、模型切换混在同一条恢复链路中。
3. 最终 `concat` 调用虽然引用了三个 Asset，但这只能证明拼接服务收到三个输入，不能反推“原定三段均正常生成”，也不能证明三个段落在最终画面中都正确可见。
4. Langfuse 中不存在 `1分19秒` 的源视频。最终三个拼接输入的媒体时长约为 `7.04秒`、`8.04秒` 和 `7.04秒`。因此，第二段显示 `1分19秒` 并在十秒后静止，是时间线时长与源媒体时长不一致造成的。

本 Case 应按“**三段规划 → 两段正式生成 → 后续临时补段和重试 → 三个 Asset 被提交拼接 → 成片仍缺段且时间线异常**”理解，而不是按一次正常的三段生产流程理解。

## 四、根因分析

### 4.1 根因一：生成任务没有与脚本分段进行完整性校验

原定三段，首轮实际只生成两段，但系统仍然继续执行。后台只看到两段视频，和 Langfuse 首轮调用完全一致。后续通过临时补生成和多次重试尝试恢复素材，而不是重新核对并完整执行三段制作方案。

这会造成两个问题：

- 不同分段的生成状态和版本不一致。
- 编辑器、拼接服务和交付层可能分别引用不同批次的 Asset。

### 4.2 根因二：预期十秒没有传递到视频生成参数

第 2 段最终生成调用明确使用了：

```json
{
  "name": "rome_egypt_seg2_reveal_k2",
  "duration": "8"
}
```

模型最终返回 `8.041667秒`，与请求的 8 秒一致。

因此，第 2 段没有达到预期十秒，不是视频模型少生成了，而是上游在调用生成模型前就把时长设置成了 8 秒。这属于制作方案到生成参数之间的传递错误。

### 4.3 根因三：编辑器时间线时长与媒体真实时长不一致

Langfuse 中没有任何最终选用素材的时长是 1 分 19 秒。后台最终拼接的预期总时长也只有约 22.13 秒。

因此，用户看到的 `1分19秒` 不可能来自本次实际视频生成参数或最终 `concat` 参数。

最符合现象的下游故障路径是：

```text
时间线 Clip 被写入错误或过期的时长
  → 真实视频在约 8 秒时播放结束
  → 播放器继续显示最后一帧
  → 剩余时间看起来一直静止
```

错误时长可能来自：

- 把项目总时长错误写入单个 Clip。
- 秒、毫秒、帧或时间码之间转换错误。
- 重试生成后仍然读取旧版本素材的时间线记录。
- 编辑器恢复项目时，用旧 Asset ID 和新时长进行了错误组合。
- 生成任务耗时或其他非媒体字段被误当成视频时长。

### 4.4 根因四：缺少最终成片级别的 QA

Agent 在拼接前探测了三个输入素材，但没有对最终成片执行：

- 最终时长校验。
- 首帧和分段边界抽帧检查。
- 第 1 段是否实际可见的检查。
- 尾部连续重复帧或静帧检测。

因此，即使时间线展示、交付 Asset 或拼接结果存在问题，当前交付门禁也无法发现。

## 五、解决方案

### 5.1 建立唯一的分段清单

在生成前建立一份唯一的分段清单，并让生成、重试、拼接、数据库和编辑器全部使用同一份数据：

```json
[
  {"sequence_id": 1, "asset_id": "a_Nooqypp", "duration": 7.041667},
  {"sequence_id": 2, "asset_id": "a_xR7ZktL", "duration": 8.041667},
  {"sequence_id": 3, "asset_id": "a_hmYRKAe", "duration": 7.041667}
]
```

重新生成某一段时，必须根据同一个 `sequence_id` 原位替换 Asset，不能追加成一个无法与原分段对应的新时间线项目。

### 5.2 增加拼接前完整性门禁

进入 assembly 之前必须满足：

```text
计划中的 sequence_id 集合
==
成功生成的 sequence_id 集合
```

任何一个分段缺失，都必须停止拼接。这条规则可以直接阻止本项目第一批漏掉第 2 段后继续执行。

### 5.3 建立时长传递和校验契约

- 用户确认的目标时长必须原样传递到 `video_generate.duration`。
- 生成完成后，以 `media_probe.derived.video_playable_seconds` 作为素材真实时长。
- 时间线 Clip 时长与实际媒体时长相差超过 `0.1秒` 时，默认阻止保存和交付。
- 只有明确配置了循环、变速、裁切、冻结尾帧或停留设计，才允许时间线时长超过源视频时长。
- 禁止使用生成耗时、项目总时长、UI 文本或旧 Asset 时长推导当前 Clip 时长。

### 5.4 完善时间线持久化字段

每个时间线 Clip 必须同时保存并校验：

```text
sequence_id
asset_id
asset_version
source_duration_seconds
timeline_in_seconds
timeline_out_seconds
explicit_end_behavior
```

时间线槽位长于源视频时，系统必须要求明确选择结束行为。不能默认无限显示最后一帧。

### 5.5 增加最终交付 QA

最终拼接完成后必须：

1. 对最终 Asset 再执行一次 `media_probe`。
2. 将最终时长与分段清单的时长总和进行比较。
3. 在 `0秒`、每个分段边界和结束前一秒抽帧。
4. 确认开头画面属于第 1 段。
5. 检测连续重复帧，非明确设计的长静帧必须阻止交付。
6. 再次核对最终分段数量、顺序和 Asset ID。

## 六、最终诊断

本项目原定三段，正式生成批次实际只生成了第 1 段和第 3 段，共两段；第 2 段没有按原计划生成。后续出现的第 2 段是异常恢复阶段的补生成，同时预期十秒被错误设置成了八秒。

恢复流程最终向 `concat` 提交了三个 Asset，输入参数中包含第 1 段，三个输入素材的实际总时长约为 22.13 秒。但该链路没有对最终文件进行 `media_probe` 和逐段视觉检查，因此不能确认第 1 段在成片中实际可见，也不能把三个输入 Asset 等同于三段生产成功。

因此，本 Case 的主根因是三段规划没有完整转化为三段正式生成任务；恢复阶段又通过补段、重复生成和模型切换临时组装素材，导致生成记录、后台展示、拼接输入和最终时间线不一致。第二段 `1分19秒` 及十秒后的静止则是时间线没有采用源视频约 8.04 秒的真实时长，并在源视频结束后持续显示尾帧。缺少最终成片时长与逐段视觉 QA，使两个问题最终进入交付结果。
