# 项目 03249823990：旁白与画面不同步、画面循环的根因与解决方案

## 结论

这不是音轨逐渐漂移，也不是单个视频素材生成失败。核心问题是生产链只为长旁白生成了少量短视频，然后把成片时长平均分配给这些视频，没有按照旁白的真实语义时间点编排画面。

初始方案计划制作 480 秒视频，却只生成 11 个、每个 10 秒的素材，总计约 110 秒。实际旁白为 348.48 秒，合成阶段将其平均划分为 11 个 31.68 秒的画面窗口。由于各旁白章节的真实长度不同，平均分配使画面主题与旁白主题错开。

随后，运行时的 `data-loop` 没有正确续播视频，约 26 秒处出现黑屏。修复方案没有补充新素材，而是将每个相同的 10 秒视频连续拼接 4 次，生成约 40 秒文件，再截取前 31.68 秒使用。这消除了黑屏，却直接制造了用户看到的重复画面。

因果链：

`480 秒长视频需求 -> 只生成 11 x 10 秒素材 -> 旁白实际缩短为 348.48 秒 -> 画面窗口被平均分为 31.68 秒 -> 语义边界没有随旁白重算 -> data-loop 运行时失效并出现黑屏 -> 同一素材连续拼接 4 次补时 -> 重复画面进入成片 -> QA 只检查单帧黑屏、总时长和响度 -> 未拦截语义错位及重复片段 -> 交付`

## 旁白与画面为什么会错位

### 1. 使用平均分段，而不是旁白真实时间戳

合成阶段采用：

```text
348.48 秒旁白 / 11 个视觉段 = 每段 31.68 秒
```

对应的画面开始时间为：

| 视觉段 | 主题 | 画面开始时间 |
|---|---|---:|
| seq_01 | Hook | 0.00s |
| seq_02 | Age is not the problem | 31.68s |
| seq_03 | 100,000 km | 63.36s |
| seq_04 | Stacked maintenance | 95.04s |
| seq_05 | Component clustering | 126.72s |
| seq_06 | Previous ownership | 158.40s |
| seq_07 | Diagnostic complexity | 190.08s |
| seq_08 | Expectation gap | 221.76s |
| seq_09 | Common mistakes | 253.44s |
| seq_10 | Smart ownership | 285.12s |
| seq_11 | Conclusion | 316.80s |

但 TTS 是按 4 个大组生成，而不是按 11 个视觉主题分别生成和计时。第二组旁白在 51.52 秒开始，其第一句话就是 stacked maintenance；对应的 `seq_04` 画面却到 95.04 秒才开始，约晚 43.52 秒。

因此，即使音轨和视频轨总时长几乎相同，主题也已经错位。这是语义同步失败，不是编解码器造成的累计时间漂移。

### 2. 原计划时长改变后没有重建视觉时间线

原脚本按 480 秒和 11 个预估段落编排，实际 TTS 只有 348.48 秒。系统只改变了总时长并平均压缩视觉段落，没有根据 TTS 的句子级时间戳重算每个主题的进入和退出时间。

结果是：总时长看似对齐，内部语义边界却不对齐。

## 画面为什么会循环

### 1. 唯一素材覆盖严重不足

实际只有约 110 秒唯一视频，却要覆盖 348.48 秒成片。每个 10 秒素材被安排承担 31.68 秒画面，天然存在至少三次重复播放需求。

### 2. 第一次循环方案在渲染层失效

合成 HTML 在 sequence 上设置 `data-duration="31.68"`，在内部 video 上设置 `data-loop="true"`。实际运行时没有按预期循环，10 秒视频结束后背景变黑。约 26 秒处的预览明确复现了字幕仍播放、背景已经消失的问题。

### 3. 黑屏修复把运行时故障转换成可见重复

为绕过 `data-loop`，Agent 将相同素材作为 4 个 concat 输入：

```text
clip_A + clip_A + clip_A + clip_A -> 约 40 秒 loop_clip_A
```

然后在 31.68 秒视觉窗口中播放该文件。该方案技术上保证了连续画面，但每 10 秒都会回到同一素材的起点，用户看到的循环因此成为确定行为。

## 根因分层

### P0：视觉覆盖规划错误

长视频生产计划只按 11 个章节生成 11 个短视频，没有将“章节”继续拆成用户要求的 4 至 6 秒视觉节拍。章节是语义结构，不应直接等同于一个素材文件。

### P0：时间轴映射错误

系统使用 `总旁白时长 / 素材数` 进行平均分配，没有使用 TTS 句子时间戳、字幕时间戳或 forced alignment 结果建立语义映射。

### P0：循环补时策略错误

素材不足时允许使用 loop 或相同素材 concat 补足长时间窗口。对于明确要求持续视觉变化的长视频，这与用户约束直接冲突。

### P0：最终交付门禁缺失

QA 只验证黑屏点、成片总时长和响度，没有检查全片重复画面与旁白语义同步。局部技术问题被修复后，新的用户可见问题没有被检测。

### P1：目标时长没有被严格执行

用户要求 7 至 8 分钟，最终旁白和成片约 5 分 48 秒。系统没有在 TTS 生成后检查实际时长是否满足需求，也没有扩充脚本或要求用户确认缩短版本。

## 已排除的替代解释

- **不是音轨逐渐漂移**：合成计划为 348.48 秒，最终视频约 348.51 秒，两者只相差约 0.03 秒。
- **不是视频文件全部生成失败**：11 个 10 秒视频均成功生成，问题是数量和覆盖策略不足。
- **不只是渲染器的循环故障**：渲染器故障解释了黑屏，但同一素材 concat 4 次才是用户看到循环画面的直接原因。
- **不是单纯的模型随机重复**：重复由相同 asset 被确定性地多次拼接产生。
- **不是用户需求含糊**：用户明确要求每 4 至 6 秒出现新的角度、运动或信息图。

## 解决方案

### P0：采用旁白优先、语义时间戳驱动的制作流程

- **Owner**：script / TTS / timeline orchestration
- 先生成最终旁白并确认实际总时长。
- 对旁白执行句子级或短语级 forced alignment，得到每个语义 cue 的真实 `start` 和 `end`。
- 每个 cue 明确绑定 `visual_asset_id`、视觉主题和允许使用的时间范围。
- 禁止通过 `总时长 / 素材数` 推导章节边界。
- 旁白内容或语速发生变化时，必须重建完整视觉时间线。

建议的数据结构：

```json
{
  "cue_id": "stacked_maintenance_01",
  "narration_start": 51.52,
  "narration_end": 57.10,
  "narration_topic": "deferred brake maintenance",
  "visual_asset_id": "brake_pad_to_disc_01",
  "visual_start": 51.52,
  "visual_end": 57.10,
  "max_sync_error_ms": 1000
}
```

### P0：按视觉变化频率计算最低素材覆盖量

- **Owner**：creative planning / generation router
- 348.48 秒成片、每 4 至 6 秒一次变化，需要约 59 至 88 个视觉节拍。
- 480 秒成片需要约 80 至 120 个视觉节拍。
- 视觉节拍可以是不同视频、信息图、结构化动画或同一长镜头中真实不重复的镜头运动，但不能是相同 10 秒素材重新开始。
- 生成前计算 `required_visual_beats`；素材不足时不得进入最终 assembly。

### P0：禁止使用重复素材静默补时

- **Owner**：assembly / media processor
- 相邻窗口不得使用相同 `asset_id + media_start`。
- 禁止使用 `[A, A, A, A]` 的 concat 输入补足持续时间。
- 源视频短于目标窗口时，只能补生成新素材、缩短窗口、使用有意义的非重复图形层，或请求用户授权静态/循环处理。
- 用户没有明确允许循环时，`loop=true` 应视为高风险并触发检查。

### P0：增加全片重复画面门禁

- **Owner**：final QA / validator
- 每 0.5 至 1 秒抽帧，使用感知哈希、SSIM 或视频指纹检测重复片段。
- 同时检查合成清单中的 asset ID 和 media offset，提前识别确定性重复。
- 检测长度超过阈值的重复序列、周期性回到相同起始帧或相邻窗口复用时，阻断交付。
- 检查范围必须覆盖全片，不能只预览一个时间点。

### P0：增加旁白语义与画面匹配门禁

- **Owner**：multimodal QA
- 按 4 至 6 秒窗口读取旁白文本和当前画面标签。
- 校验画面主题是否支持当前旁白，而不是只检查视频是否持续播放。
- 关键章节画面进入时间相对旁白 cue 的误差建议不超过 1 秒。
- 总时长对齐和语义对齐必须同时通过。

### P1：严格校验用户要求的总时长

- TTS 完成后立即测量时长。
- 若实际时长不在 420 至 480 秒范围内，应扩充脚本、调整语速，或请求用户确认接受较短版本。
- 未满足用户时长约束时，不应以“技术上已渲染完成”作为交付依据。

## 回归测试

1. **视觉覆盖测试**：348.48 秒且要求每 4 至 6 秒变化时，断言视觉计划至少包含 59 个有效节拍。
2. **平均分段禁用测试**：不同长度的旁白章节不得产生完全相同的视觉窗口时长，除非 forced alignment 的结果确实相同。
3. **语义边界测试**：stacked maintenance 等章节的目标画面应在对应旁白开始后 1 秒内进入。
4. **重复素材参数测试**：`media_process.inputs` 不得出现连续相同 asset ID 和相同 media start。
5. **循环策略测试**：用户未授权循环时，任何 `loop=true` 或源时长短于窗口时长的片段都必须触发失败或补素材流程。
6. **视频指纹测试**：构造 `[A, A, A, A]` 成片，确保重复检测能够识别约 10 秒周期并阻止交付。
7. **黑屏回归测试**：从每个源素材结束点前后抽帧，确认没有黑帧；修复黑屏后仍必须重新执行重复检测。
8. **全片 QA 测试**：验证器必须覆盖 0 秒至成片结束，不能只检查单个预览点。
9. **总时长测试**：用户要求 7 至 8 分钟时，低于 420 秒或高于 480 秒必须阻断交付。
10. **交付测试**：重复检测、语义同步、黑帧、旁白/字幕同步、时长和音频响度全部通过后，才允许调用最终交付工具。

## 修复后的预期链路

`确认 7-8 分钟目标 -> 生成并测量最终旁白 -> 句子级 forced alignment -> 每 4-6 秒建立视觉 cue -> 计算最低素材量 -> 生成足够的不重复视频和信息图 -> 按 cue 时间戳合成 -> 全片黑帧、重复指纹和语义同步检查 -> 时长与音频 QA -> 仅全部通过后交付`
